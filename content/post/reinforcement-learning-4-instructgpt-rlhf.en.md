A pretrained language model learns patterns in text by predicting the next token. Training it to answer questions and follow instructions also requires demonstrations and preference data.

InstructGPT uses three training stages: SFT learns from demonstrated answers, a Reward Model learns to evaluate answers, and PPO updates the policy using those rewards.

The three stages can be followed in the Python files in [`chapter08_rlhf`](https://github.com/walkinglabs/hands-on-modern-rl/tree/main/code/chapter08_rlhf). Complete source files are available at the end.

## 1. Data and outputs of the three stages

| Stage | Data | Learning signal | Main artifact |
| --- | --- | --- | --- |
| SFT | Input and demonstration answer | Increase the likelihood of demonstrated answers | An instruction-following policy initialization |
| Reward Model | A prompt with chosen and rejected answers | Score preferred answers higher | A scalar reward model |
| PPO | Prompts and answers generated by the current policy | Increase rewarded behavior while controlling drift | An updated policy |

The same training prompt can serve different stages, but its supervision changes. SFT needs an example of what to say. RM training needs a comparison. PPO rollouts usually need only the prompt: the Actor generates the answer.

For a question about PPO, SFT might provide a clear demonstration; RM training might compare an accurate explanation against a vague one; PPO scores a newly generated explanation and updates the model. **PPO does not need a correct answer token at every position, but it does need a trustworthy reward signal.**

The source files save their outputs here:

```text
sft_pipeline.py
  → output/sft_results/sft_model

reward_model_training.py
  → output/rm_results/value_head.pt

rlhf_ppo_train.py
  → output/ppo_results/aligned_model
```

## 2. Step 1: SFT learns from demonstrations

### From plausible continuation to useful task completion

A pretrained language model predicts the next token. Given “Explain reinforcement learning,” it might explain the concept, or continue with “Explain supervised learning” and “Explain unsupervised learning.” A list of questions can be a plausible continuation of a document.

Supervised Fine-Tuning selects demonstrations that show the behavior we want from an assistant:

```json
{
  "messages": [
    {"role": "system", "content": "You are a clear, honest and concise reinforcement learning tutor."},
    {"role": "user", "content": "What is a value function?"},
    {"role": "assistant", "content": "A value function estimates the expected cumulative return from a state under a policy."}
  ],
  "source": "human_written",
  "quality": "verified"
}
```

`source` and `quality` are dataset metadata, not text the assistant must generate.

### What the SFT loss optimizes

For prompt `x` and demonstration answer `y`, an answer-only negative log-likelihood is:

<div class="math-display">
\[
L_{\mathrm{SFT}}(\theta)
=-\sum_{t=1}^{T}\log\pi_\theta(y_t\mid x,y_{\lt t}).
\]
</div>

`θ` denotes model parameters, `y_t` the demonstrated token at position `t`, `y_<t` its **correct demonstration prefix**, and `T` the answer length. The logarithm is natural; the minus sign turns probability maximization into loss minimization. Implementations generally also average over valid tokens or a batch.

If the next token should be “Paris” and the model assigns probability 0.1, its loss contribution is about 2.303. At probability 0.8, that becomes about 0.223. Backpropagation pushes up the probability of the demonstrated token in similar contexts.

This is teacher forcing: training conditions on the demonstration prefix rather than repeatedly feeding back the model's own errors. The objective remains next-token prediction; the selected data and supervised positions change.

### Source: examples and the chat template

In [`sft_pipeline.py`](https://github.com/walkinglabs/hands-on-modern-rl/blob/051b2ff0210c718091692d37ee26d08613ad0be8/code/chapter08_rlhf/sft_pipeline.py), `generate_sft_data()` returns handwritten instruction-response pairs covering mathematics, writing, programming and general knowledge. Although the comments call them Self-Instruct-style data, the script **does not call another model to generate them**.

The list contains **14 examples**; the printed category counts overcount by one. This small dataset demonstrates the training process.

`format_sft_dataset()` performs this transformation:

```python
messages = [
    {"role": "user", "content": pair["instruction"]},
    {"role": "assistant", "content": pair["response"]},
]
text = tokenizer.apply_chat_template(
    messages,
    tokenize=False,
    add_generation_prompt=False,
)
formatted_texts.append(text)
```

The template inserts the model's expected role boundaries. A training example already includes the assistant answer, so it does not need an additional generation prefix. Inference, with only a user question, uses `add_generation_prompt=True`.

The resulting dataset is `Dataset.from_dict({"text": formatted_texts})`: a column of complete conversation strings.

### Source: training settings and loss masking

`SFTTrainer` runs the training:

```python
sft_config = SFTConfig(
    output_dir="./output/sft_results",
    per_device_train_batch_size=2,
    learning_rate=2e-5,
    num_train_epochs=2,
    max_length=512,
    logging_steps=1,
    save_strategy="epoch",
    report_to="none",
    fp16=False,
)

trainer = SFTTrainer(
    model=model,
    args=sft_config,
    train_dataset=train_dataset,
    processing_class=tokenizer,
)
train_result = trainer.train()
```

The checkpoint, **Qwen/Qwen2.5-0.5B-Instruct**, is already instruction-tuned. This stage continues fine-tuning it.

The script puts the whole conversation in `text` without an answer mask. Under TRL 0.24.0 defaults, system, user and assistant text all contribute to the language-modeling loss; the equation above supervises only the answer. The chat template determines formatting, not which tokens contribute to loss.

To supervise only answers, separate prompt and completion or construct labels that ignore non-answer positions. Conceptually:

```python
# Illustration: prompt and full-sequence token boundaries must align correctly.
labels = input_ids.clone()
labels[:prompt_length] = -100
labels[attention_mask == 0] = -100
```

`-100` is an ignored loss label, not a token ID. The model still attends to the prompt; it is simply not trained to reproduce it.

TRL 0.24.0 supports `assistant_only_loss=True` for conversational data with a template that returns an assistant mask. This approach also requires converting the existing plain `text` data to the corresponding conversation structure. See the [SFT documentation](https://huggingface.co/docs/trl/v0.24.0/en/sft_trainer).

SFT saves the model and tokenizer. The next stage uses preference pairs to train RM to rank answers.

## 3. Step 2: a Reward Model learns comparisons

### Preference data need not define one perfect answer

“Accurate, helpful and clear” is difficult to encode as exhaustive rules. Comparing two answers can be easier:

```json
{
  "prompt": "Explain the KL penalty in PPO-RLHF.",
  "chosen": "It discourages the policy from drifting too far from a reference model while pursuing reward.",
  "rejected": "The KL penalty is a mathematical formula. PPO uses it, so it is important.",
  "labeler": "human_or_judge",
  "rubric": ["accuracy", "helpfulness", "clarity"]
}
```

An RM consumes the complete prompt and answer, and produces a real-valued score `r_φ(x,y)`, with parameters `φ`. Rather than generating an explanation, it learns to score chosen answers higher.

### From a score difference to a preference probability

Let `y_w` be the preferred answer and `y_l` the other answer. Their margin is:

<div class="math-display">
\[
m=r_\phi(x,y_w)-r_\phi(x,y_l).
\]
</div>

The Bradley–Terry formulation maps it to a probability:

<div class="math-display">
\[
P_\phi(y_w\succ y_l\mid x)=\sigma(m),
\qquad \sigma(m)=\frac{1}{1+e^{-m}}.
\]
</div>

The label tells us that the annotator selected `y_w`. Maximizing its probability gives this negative log-likelihood:

<div class="math-display">
\[
L_{\mathrm{RM}}(\phi)
=-\log\sigma\!\left(r_\phi(x,y_w)-r_\phi(x,y_l)\right).
\]
</div>

A margin of `2` gives preference probability about 0.881 and loss about 0.127. At `0`, these are 0.5 and 0.693. At `-2`, the ordering is reversed and loss rises to about 2.127.

**Wrong ordering is penalized; a stronger lead for the chosen answer reduces loss.** This does not prove the chosen answer is correct in every respect. It identifies the preferred member of this comparison.

### Source: a scalar head on the last valid token

[`reward_model_training.py`](https://github.com/walkinglabs/hands-on-modern-rl/blob/051b2ff0210c718091692d37ee26d08613ad0be8/code/chapter08_rlhf/reward_model_training.py) formats chosen and rejected responses separately with the same prompt, then tokenizes each sequence up to 256 tokens.

`RewardModel` adds `nn.Linear(hidden_size, 1)` to a language-model backbone. Its core forward pass, with comments omitted, is:

```python
outputs = self.base_model(
    input_ids=input_ids,
    attention_mask=attention_mask,
    output_hidden_states=True,
)
last_hidden = outputs.hidden_states[-1]
sequence_lengths = attention_mask.sum(dim=1) - 1
batch_size = input_ids.shape[0]
last_token_hidden = last_hidden[
    torch.arange(batch_size), sequence_lengths
]
reward = self.value_head(last_token_hidden).squeeze(-1)
```

Shapes progress as `input_ids: [B,L] → last_hidden: [B,L,H] → last_token_hidden: [B,H] → reward: [B]`. The final valid position can attend to the preceding sequence and provide a representation for scoring.

The indexing rule `attention_mask.sum()-1` assumes **right padding**. It is not a general last-valid-position rule for left padding. The 256-token limit can also truncate the end of an answer, so check what the scorer actually sees.

This `value_head` outputs an answer's reward score. A PPO Critic estimates future return; the training targets differ.

The essential training code is:

```python
r_chosen = model(chosen_ids, chosen_mask)
r_rejected = model(rejected_ids, rejected_mask)
loss = -torch.log(torch.sigmoid(r_chosen - r_rejected)).mean()

optimizer.zero_grad()
loss.backward()
optimizer.step()
```

`-F.logsigmoid(r_chosen - r_rejected).mean()` is a mathematically equivalent, more numerically stable formulation.

### Accuracy, margins and the limits of score interpretation

The script counts `r_chosen > r_rejected` as correct. It actually defines **19 pairs**, split into 16 training pairs and 3 test pairs—not 20 and 4 as some comments suggest. With three test examples, accuracy moves in increments of roughly 33.3 percentage points. It is not a robust generalization estimate.

Margins can reveal collapsed scoring, but bigger is not inherently better. Pairwise loss supplies no natural absolute reward scale. A shared score offset leaves comparisons unchanged, while rescaling scores changes downstream RL incentives. Check held-out rankings, score distributions, length correlations and actual examples together.

In particular, politeness, length and numbered lists are not equivalent to correctness and helpfulness. If longer answers systematically win in the dataset, RM may learn that shortcut and PPO may amplify it.

### Why saving only the head breaks the handoff

The optimizer receives `reward_model.parameters()`. The backbone is not frozen, so **both backbone and head are updated**. Saving, however, only writes:

```python
torch.save(
    reward_model.value_head.state_dict(),
    os.path.join(save_dir, "value_head.pt"),
)
```

The PPO script subsequently reloads the original Qwen backbone and attaches this head. It **does not restore the trained RM**: the representation entering the head has changed.

Restoring the full RM requires the trained backbone, head, tokenizer and configuration. Fixed examples can check that scores stay the same after reloading. Saving only the head is sufficient if the backbone was frozen from the start and only the head was trained.

## 4. Step 3: PPO learns from reward

### Language generation as sequential decision-making

For a prompt `x`, the model generates an answer one token at a time:

| RL element | Language-generation counterpart |
| --- | --- |
| State | Prompt and generated answer prefix |
| Action | Next token |
| Policy | The model's next-token probability distribution |
| Transition | Append the token to the prefix |
| Episode | Generation until EOS or the length limit |
| Task reward | RM score for the complete prompt-answer pair |

RM often supplies a score only at the end. This creates a credit-assignment problem: did the answer fail near the beginning, or go off track much later? Critic-based advantage estimation helps turn returns into more stable token-level update signals.

### Four logical roles, two trainable roles

| Role | Function | Updated? |
| --- | --- | --- |
| Actor | Generate answers and learn rewarded behavior | Yes |
| Reference | Frozen SFT anchor for controlling drift | No |
| Reward Model | Score complete answers | Usually frozen during the PPO phase |
| Critic | Predict future return from the current prefix | Yes |

These roles can share parts of a model. RM scores an answer; Critic predicts future return from the current prefix and supplies a baseline for advantage estimation.

### Why subtract a KL penalty?

Maximizing RM alone may teach the Actor to exploit its judge, for example by producing long, apparently thorough answers that do not solve the task.

A sequence-level objective is:

<div class="math-display">
\[
\begin{aligned}
J(\theta)&=\mathbb E_{x}\Bigl[
\mathbb E_{y\sim\pi_\theta(\cdot\mid x)}r_\phi(x,y)\\
&\qquad-\beta D_{\mathrm{KL}}\!\left(
\pi_\theta(\cdot\mid x)\,\|\,\pi_{\mathrm{ref}}(\cdot\mid x)
\right)\Bigr].
\end{aligned}
\]
</div>

`π_θ` is Actor, `π_ref` is the frozen reference, `·` ranges over possible answers, and `β` sets the strength of the penalty. The RM parameters `φ` and Actor parameters `θ` are different.

KL compares **conditional distributions over answers**, not the surface difference between two texts. For an answer sampled from the current policy, a sampled score is:

<div class="math-display">
\[
\widetilde R(x,y)=r_\phi(x,y)
-\beta\log\frac{\pi_\theta(y\mid x)}{\pi_{\mathrm{ref}}(y\mid x)}.
\]
</div>

Its log-ratio has the sequence KL as its expectation under the current policy. Individual log-ratios can be negative: **one sampled log-ratio is not itself a guaranteed nonnegative KL divergence**.

During rollouts, a temporarily fixed `π_old` typically generates data. A token-level shaped reward can be written:

<div class="math-display">
\[
\begin{aligned}
k_t&=\log\frac{\pi_{\mathrm{old}}(y_t\mid s_t)}
{\pi_{\mathrm{ref}}(y_t\mid s_t)},\\
\widetilde r_t&=-\beta k_t
+\mathbf 1_{t=T}\,r_\phi(x,y).
\end{aligned}
\]
</div>

Each step receives its reference penalty, and the final valid answer token receives the task reward. Alternative implementations exist, but the KL must actually affect updates through reward shaping or a differentiable objective—not merely appear in logs.

### Critic and advantage: better than expected by how much?

`V_ψ(s_t)` predicts the expected return from the current prefix. Advantage is positive when outcomes exceed that expectation, and negative when they disappoint. A common GAE form is:

<div class="math-display">
\[
\begin{aligned}
\delta_t&=\widetilde r_t+\gamma V_\psi(s_{t+1})-V_\psi(s_t),\\
\widehat A_t&=\sum_{l=0}^{T-t}(\gamma\lambda)^l\delta_{t+l}.
\end{aligned}
\]
</div>

Terminal value is usually zero; length truncation may require different bootstrapping treatment. `γ` discounts future reward, and `λ` controls the bias-variance tradeoff. The Critic also needs a value-regression loss; calculating advantages does not train it automatically.

### PPO clipping and reference KL serve different purposes

PPO compares the new policy with the **old rollout policy**:

<div class="math-display">
\[
\rho_t(\theta)=
\frac{\pi_\theta(y_t\mid s_t)}{\pi_{\mathrm{old}}(y_t\mid s_t)}.
\]
</div>

It then maximizes the clipped surrogate:

<div class="math-display">
\[
\begin{aligned}
L_{\mathrm{clip}}(\theta)=\mathbb E_t\Bigl[\min\bigl(&
\rho_t(\theta)\widehat A_t,\\
&\operatorname{clip}(\rho_t(\theta),1-\epsilon,1+\epsilon)
\widehat A_t\bigr)\Bigr].
\end{aligned}
\]
</div>

Positive advantage encourages a probability increase, without continuing to reward excessive increases. Negative advantage encourages a decrease, with an analogous limit on the incentive. Clipping changes the objective; it is not a hard guarantee that every probability ratio stays inside the interval.

**Old policy is refreshed for rollout batches; Reference remains a longer-lived SFT anchor.** Clipping controls local updates, whereas reference KL controls drift from that anchor. Their denominators are not interchangeable. See the [PPO paper](https://arxiv.org/abs/1707.06347) for its repeated minibatch-update formulation.

## 5. Reading the PPO implementation

### Initializing Actor and Reference

[`rlhf_ppo_train.py`](https://github.com/walkinglabs/hands-on-modern-rl/blob/051b2ff0210c718091692d37ee26d08613ad0be8/code/chapter08_rlhf/rlhf_ppo_train.py) tries to load the saved SFT model, falling back to the original Qwen Instruct checkpoint when unavailable.

```python
reference_model = copy.deepcopy(policy_model)
reference_model.eval()
for param in reference_model.parameters():
    param.requires_grad = False
```

Reference is a frozen copy of Actor. The script defines its own `PPOTrainer` class, separate from TRL's class of the same name.

### The reward can be heuristic or mixed

Without `value_head.pt`, `SimpleRewardModel` scores length, lists, code fences and polite language. With a head, it reloads a Qwen backbone and returns:

```python
return 0.5 * reward + 0.5 * rule_score
```

This is not necessarily a pure human-preference RM. Equal coefficients also do not imply equal influence when the score scales differ.

Rules can be exploited too: an irrelevant answer containing polite phrasing, numbered steps and code fences may score well. Format checks are not semantic verification, and higher reward is not automatically greater usefulness.

### Advantage without a Critic or GAE

The script computes:

```python
rewards_tensor = torch.tensor(batch_rewards, dtype=torch.float32)
advantages = rewards_tensor - rewards_tensor.mean()
advantages = advantages / (advantages.std() + 1e-8)
```

Each answer receives one standardized scalar. The batch contains different prompts, mixing question difficulty and reward scales. This is neither a learned prefix-conditioned baseline nor GRPO's within-prompt comparison of multiple candidates.

The generated positions in an answer therefore share one scalar, whereas standard Actor-Critic PPO estimates token-level advantages from the states at each position.

### Averaging log probabilities changes what the ratio means

`compute_log_probs()` aligns logits and next-token targets:

```python
shift_logits = logits[:, :-1, :]
shift_labels = input_ids[:, 1:]
log_probs = F.log_softmax(shift_logits, dim=-1)
token_log_probs = log_probs.gather(
    2, shift_labels.unsqueeze(-1)
).squeeze(-1)

shift_mask = attention_mask[:, 1:]
token_log_probs = token_log_probs * shift_mask
return token_log_probs.sum(dim=-1) / shift_mask.sum(dim=-1)
```

Shift and gather are familiar causal-LM operations. But the final result is the **mean log probability across valid tokens**, and the sequence includes both prompt and response. The mask excludes padding, not prompt tokens.

The joint log probability of an answer sums over **answer tokens**. Token-level PPO instead retains individual answer-token log probabilities and a response mask. Mixing prompt positions, averaging and then exponentiating does not yield either standard ratio.

`input_len` is available but unused for response masking. If prompt length is `P`, shifted position `P-1` predicts the first response token; correcting the mask requires care with that offset.

### Clipping is written down, but rollouts are not reused

The script stores pre-update Actor log probabilities and computes:

```python
ratio = torch.exp(new_log_prob - old_log_p)
surr1 = ratio * advantage
surr2 = torch.clamp(
    ratio, 1.0 - self.clip_range, 1.0 + self.clip_range
) * advantage
policy_loss = -torch.min(surr1, surr2)
```

`old_log_p` comes from the pre-update Actor. The class docstring incorrectly names Reference as the denominator, contrary to the implementation.

There is only one `optimizer.step()` per rollout batch. With deterministic forward passes and unchanged parameters, the ratio starts at 1. The gradient can still be nonzero, but clipping does not constrain subsequent updates on the same batch because there are none. Dropout-induced differences would not be evidence of a meaningful policy update either.

Generation also uses temperature and top-p, whereas likelihoods use unmodified logits. The behavior distribution and ratio probabilities are not strictly consistent. This illustrates a loop, not an experiment validating PPO's clipping mechanism.

### KL does not contribute to the gradient

`compute_kl_divergence()` computes vocabulary KL at visited prefixes under `torch.no_grad()`, then returns `kl_div.item()`, a Python float. Training adds those floats to the loss:

```python
avg_kl = sum(batch_kl) / len(batch_kl)
kl_penalty = self.kl_coef * avg_kl
total_loss = avg_policy_loss + kl_penalty
total_loss.backward()
```

**The logged total loss includes KL, but its gradient does not.** Adding a detached constant cannot change the policy-loss derivative. Advantages do not include KL either, so there is no alternative shaping path enforcing it.

Two common designs can make KL matter:

- Put the sampled reference log-ratio into token rewards, then compute returns and advantages from those rewards. These rewards may be detached because they subsequently weight the policy gradient.
- Add a differentiable KL objective during optimization. Preserve the Actor graph, freeze Reference, and reduce only over the intended answer positions.

For the second approach, the KL term can be calculated as follows:

```python
policy_logp = F.log_softmax(policy_logits, dim=-1)
with torch.no_grad():
    ref_logp = F.log_softmax(ref_logits, dim=-1)

kl_per_token = (
    policy_logp.exp() * (policy_logp - ref_logp)
).sum(dim=-1)
kl_loss = (kl_per_token * response_mask).sum() / response_mask.sum()
loss = policy_loss + beta * kl_loss
```

The logits must be shifted and aligned with next-answer-token targets, and the nonempty response mask must exclude prompt and padding. This fragment calculates differentiable KL; the training loop still handles old-policy state, value loss, advantages and minibatch updates.

## 6. How to tell whether RLHF actually helped

RM is a proxy. An Actor can become better at exploiting it while becoming less useful to users. Keep at least three evaluation layers: fixed tasks for capabilities and instruction following; blinded SFT-versus-RLHF preference comparisons; and human inspection of high-scoring outputs.

| Check | What it establishes | Warning sign |
| --- | --- | --- |
| SFT loss and held-out performance | Learning versus overfitting | Training improves while held-out results worsen |
| RM accuracy and margins | Generalization of rankings | Preference for length, politeness or templates |
| Reference KL | Rate of drift from initialization | Rapid growth, or a penalty that is only logged |
| Length and repetition | Whether superficial features inflate reward | Increasing verbosity and repetitive filler |
| Preference wins and capabilities | Better preferences without major regressions | Reward rises while blind tests or code tests worsen |

The scripts record before/after examples, RM test results and reward/KL/length plots. Capability regression tests and blinded preference comparisons require additional evaluation data.

Feedback provenance also matters:

| Source | Useful for | Risk |
| --- | --- | --- |
| Human annotation | High-quality demonstrations, calibration and final evaluation | Cost and inter-annotator consistency |
| AI Judge / RLAIF | Scaling comparisons and iteration | Amplifying judge biases |
| Rule-based verification | Math answers, code tests and format constraints | Incomplete checkers can be exploited |
| Online feedback | Finding real needs and failures | Likes and copying behavior are noisy, not ground truth |

Human preferences, AI judgments and rules provide different training signals. This example uses predefined preference pairs and adds rule-based scores during PPO.
