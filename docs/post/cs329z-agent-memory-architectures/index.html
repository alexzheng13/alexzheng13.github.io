一个助手可以在当前对话里给出很好的答案，但到了下一次会话，又需要你重新交代偏好、解释项目、重复上一轮已经完成的工作。它也许很会推理，却没有把这些能力接到一段持续的经历上。

Agent Memory 要解决的，就是这种跨时间的不连续：把过去的交互转成以后能够取回、更新，并正确用于行动的信息。

上一篇 Context Management Patterns讨论了每次模型调用应该看到什么。这篇进一步讨论：信息离开当前窗口之后，应该保存成什么、什么时候写入与召回，以及怎样证明记忆真的改善了后续任务。

1. 没有记忆，Agent 会失去什么？

讲义把问题分成三类：

  • Loss of Procedure：每次都要重新教它任务应该怎样做；
  • Loss of Knowledge：重要事实、规则和偏好没有跨会话保留；
  • Loss of Progress：任务变长后，忘记已经做过什么、早期目标与用户要求。

对应地，记忆能够带来个性化、从经验中学习，以及有状态的持续工作。

例如，用户说“接着改上次的研究计划”。一个有用的助手需要找回计划文件、尚未解决的问题、已经接受的修改意见，以及当前有效的限制。仅仅记住“用户正在写研究计划”，还不足以接着工作。

因此，记忆质量最终要体现在下一次任务上：是否减少重复解释，是否避免重复错误，是否保留了尚未完成的承诺。

2. 四种记忆：当前状态、过去经历、事实与技能

讲义借用 CoALA（Cognitive Architectures for Language Agents）的框架，把记忆按内容和用途区分。

讲义第 16 页，原图来自 CoALA 论文。

类型 主要保存什么 示例 使用方式
Working Memory 当前可见的任务状态与信息 当前目标、最新工具结果、相关代码 直接参与本轮推理，通常体现在上下文中
Episodic Memory 过去发生的具体经历 一段对话、一次失败的测试、一个任务轨迹 回查事件、恢复证据与历史
Semantic Memory 提炼出的事实和知识 用户偏好、项目规则、环境特征 回答问题或约束当前决策
Procedural Memory 如何完成任务 技能代码、操作流程、排错方法 指导或执行后续行动

同一次经历可能产生多种记忆。例如，一次部署失败可以保存为原始日志；从中提炼出“发布前要检查配置版本”；再形成一份发布检查流程。它们分别偏向情景、语义与程序性记忆。

参数记忆与上下文记忆是另一条轴

模型权重中已经包含大量知识和行为模式，也可以通过微调改变。外部事实、技能文件和历史对话，则要被读入上下文后才能用于当前生成。

这与前面的内容分类并不冲突：同一种知识可以存在于参数中，也可以保存在外部存储中。

讲义把参数侧的 Episodic Memory 标为不适用，可以理解为：模型权重不能代替一套能够精确查回某次交互的个人事件档案。 这并不意味着模型绝不会记住训练样本，而是强调可追踪历史与参数知识的用途不同。

3. 架构先回答 What、When、How

选文件系统、数据库或知识图谱之前，需要先回答三个问题。

What：保存与召回什么？

是用户事实、偏好、成功轨迹、失败经验，还是会话进度？原始日志与提炼结论是否同时保留？一个临时假设是否有足够证据成为长期记忆？

When：什么时候读写？

记忆操作可以由 Agent 按需调用，也可以由后台任务、会话结束、工具事件或其他条件触发。

实时写入让信息更快可用，但会增加当前任务延迟；后台整理能够做更充分的合并与校验，但要处理新旧状态并存的问题。

How：使用什么存储与检索机制？

存储方式 优势 需要解决的问题
文件系统 可读、可编辑，自带目录层次；可用 ls、搜索与读取工具操作 命名、索引、并发修改和信息重复
数据库 易于按用户、时间、来源等字段筛选；可组合向量与词法检索 Schema、查询质量、更新一致性
知识图谱 显式表达实体与关系，适合关系查询 抽取错误、实体消歧、关系更新与维护成本

向量检索适合语义近邻，BM25 适合精确词项，SQLite 等结构化存储适合元数据筛选。它们可以组合，和之前 RAG 章节中的检索取舍相通。

存储介质只解决一部分问题。 一个文件目录如果没有有效的读取策略，可能成为杂乱档案；一个向量库如果没有更新机制，也可能持续召回过时偏好。

4. 模式一：从经历中学习程序与技能

这类架构把过去有用的行动提炼成可以复用的程序性记忆。下一次遇到类似任务时，Agent 不必从头探索。

Voyager：把成功行为保存成可执行代码

Voyager在 Minecraft 中组合自动课程、反馈驱动的代码改进与 Skill Library。技能库保存代码及其描述，后续任务根据需要检索、调用或组合已有技能。

讲义第 32 页。

例如，“采矿”“熔炼”“制作工具”可以成为较小的能力单元，复杂任务再复用这些程序。讲义中的消融案例显示，技能库帮助系统在所展示实验中完成钻石工具制作；没有技能库的配置未达成同一目标。

这里的学习发生在外部代码与检索层面，并不要求同步更新基础模型权重。

AWM：从轨迹中归纳可重复工作流

Agent Workflow Memory（AWM）提取常见的操作套路。它从任务轨迹中归纳工作流，再把有关的流程提供给 Agent，指导后续行动。

讲义第 35 页。

比如，“进入商品分类 → 选择子分类 → 浏览结果”，或“定位字段 → 修改值 → 保存”。提炼时应把具体商品名、用户 ID 等换成参数，保留可迁移的操作结构。

Skill Files：把方法变成可按需加载的资产

技能也可以保存为说明文件、示例与脚本。它们适合通过 Progressive Disclosure 加载：先暴露简短能力描述，任务需要时再读详细步骤。

这类记忆的共同风险是环境变化。网站结构、API、权限和业务规则发生变化后，过去成功的流程可能不再有效。因此，技能需要适用条件、版本与验证，而不是只记录“曾经成功”。

5. 模式二：分层记忆，让有限上下文连接长期存储

分层架构让当前上下文承载少量活跃信息，把更多历史和知识保存在外部，并通过工具按需调入。

MemGPT：让模型参与管理自己的记忆

MemGPT 的核心思路是给模型提供读写记忆的工具。讲义图中，System Instructions、可修改的 Working Context 和 FIFO 消息队列处于有限窗口内；外部则包含 Recall Storage 和 Archival Storage。

讲义第 44 页，原图来自 MemGPT 论文。

三个部分的用途不同：

  • Working Context：当前重要的事实、偏好和状态，可以写入或替换；
  • Recall Storage：保存以前的交互记录，按内容或时间查找；
  • Archival Storage：保存更大规模的信息，通过检索恢复相关内容。

不必检索已经在当前窗口里的 Working Memory；真正需要解决的是何时把外部信息调进来，以及调入后应该替换什么。

MemoryOS：增加中期层与用户长期画像

MemoryOS区分 Short-term、Mid-term 和 Long-term Personal Memory，并围绕存储、更新、检索和生成构建流程。

讲义第 49 页。

中期层承接近期多轮对话，长期层保存更稳定的信息。这样，不必让一次临时表达立刻成为长期画像，也不必在近期记录离开窗口时丢掉全部结构。

分层带来的代价是管理复杂度：哪些信息应该晋升、降级、合并或过期？如果调度错误，长期记忆可能丰富，但当前任务依然拿不到正确证据。

6. 模式三：通过反思，把经历转成可复用结论

原始轨迹记录“发生过什么”，反思尝试提炼“从中学到了什么”。

Reflexion：从反馈中保留改进经验

讲义回顾了 Reflexion：Actor 执行任务，Evaluator 提供反馈，Self-reflection 将失败或不足转成语言经验，并在后续尝试中使用。

例如，第一次测试失败后留下的有用经验，应指出漏检的条件和下一次应采取的检查，而不是只写“以后更仔细”。这延续了 Reasoning 文章中的反思机制，但关注点转向经验如何被保存与复用。

Generative Agents：记忆流、检索、计划与反思

Generative Agents 把观察写入 Memory Stream，检索与当前情境相关的记忆，再用于行动、计划和更高层的反思。

讲义第 54 页。

讲义的检索示例同时考虑 Recency、Importance、Relevance：一条记忆有多新、是否重要、与当前问题是否相关。

讲义第 55 页。

可以用下面的示意式理解这种加权选择；具体归一化和权重取决于实现：

\[ S(m,q)=\alpha R_{\mathrm{recency}}(m) +\beta I(m)+\gamma R_{\mathrm{relevance}}(m,q) \]

只看语义相似度，可能错过最近变化的事实；只看时间，又可能丢掉长期重要承诺。多个信号共同决定哪些记忆值得进入当前上下文。

反思增加了抽象，也增加了推断出错的可能。例如，从“用户连续两天点素食”直接推出“用户永远不吃肉”，就把有限观察扩张成了未经确认的偏好。反思结论应保留证据和不确定性。

7. 模式四：维护记忆，持续更新与遗忘

长期系统的难点会从“怎么写进去”逐渐转向“怎样保持可用”：去重、解决冲突、更新索引、关联已有知识，并删除或失效过时信息。

Sleep-time Compute：利用请求之间的时间整理上下文

Sleep-time Compute在用户查询到来之前，对已知上下文进行离线处理，预先构建可能有用的信息，以减少后续任务的即时计算。

讲义第 58 页。

讲义把它放在记忆维护部分。它不必真的发生在夜间：关键是把可提前完成的整理移出用户等待的关键路径。收益取决于未来查询是否可预测，以及整理成本能否被多次复用摊销。

A-Mem：让记忆的组织也具有主动性

A-Mem把新交互整理为带描述、关键词和标签的笔记，并寻找与旧记忆的关联。新信息加入后，还可以触发既有记忆表示的更新。

讲义第 62 页。

这让“写一条记录”成为组织知识网络的过程，而不只是向数据库追加一行。对应的挑战是：自动生成的关联和描述也可能有错，需要回到原始证据检查。

Mem0：让新信息触发明确的更新动作

讲义中的 Mem0 流程先抽取候选记忆，再检索相关记录，检测冲突并选择更新方式：

1
2
3
4

ADD      新事实，加入记录
UPDATE   已有事实变化，更新当前表示
DELETE   移除不再应保留的记录
NOOP     没有必要改变当前记忆

讲义第 64 页。

例如，“以前周二有空，现在改成周四”不应简单保存为两条没有时间关系的偏好。系统需要区分历史状态与当前有效状态，避免召回时把两者同时当成现状。

这里的 DELETE 是记忆算法的更新动作，不能直接等同于底层备份、缓存和日志中的彻底删除。产品层的数据删除还需要独立处理。

8. 四类架构可以怎样组合？

讲义的四种模式处理不同问题，可以共存：

模式 保存内容 常见写入时机 主要收益 主要代价
从经历学习程序 代码、工作流、技能 成功轨迹之后或离线归纳 减少重复探索 流程可能过期
分层记忆 活跃信息与外部细节 新信息到达、窗口压力增大时 有限上下文连接更大存储 依赖可靠调度与召回
反思式整合 经验、规律、高层结论 获得反馈或积累观察后 提高复用与迁移能力 可能产生无依据推断
记忆维护 更新后的事实、关联与索引 新证据、写入或后台运行时 保持记忆新鲜且有组织 消耗计算，也可能误删信息

例如，一个研究助手可以保存完整任务轨迹，用工作记忆维持当前进度，从成功的检索任务中形成流程，并在后台更新项目事实。它们共享同一条闭环：经历进入系统，记忆影响下一次行动，新的结果再反过来修正记忆。

9. 记忆评测：从“答得出”走向“做得到”

讲义提出四个标准：Realistic、Long-context、Challenging、Verifiable。来源和问题要接近实际任务，历史足够长，难度足以区分系统，而且成功与失败应有明确依据。

Benchmark 记忆来源 主要能力 评测时应注意
LoCoMo 长期模拟人物对话 跨会话事实、时间关系、多跳问答等 对话回忆不等于完成 Agent 任务
PersonaMem 模拟用户与助手交互 动态用户画像与偏好变化 选择合适回答与实际行动仍有距离
LongMemEval-V2 Web Agent 历史轨迹 环境状态、工作流、易错点与前提判断 检索结果、读取模型和计算预算都影响成绩
MemoryArena 相互依赖的多会话任务 用先前经历指导后续实际操作 失败也可能来自规划、工具与执行能力

LoCoMo：长对话里找得到，也要用得对

LoCoMo 包含长对话上的问答、事件总结等任务。讲义展示了用不同记忆单元做 RAG 的结果，并强调：即使模型找到了相关记忆，也未必能正确回答。

讲义第 71 页。

这提醒我们把两种错误分开：一是没有召回正确证据，二是拿到证据后仍然理解或推理错误。仅提高 Recall 不能自动解决后者。

PersonaMem：偏好会变，当前回答也要随之变化

PersonaMem 更关注用户画像的演进。用户过去喜欢某类食物，后来改变了偏好；助手要根据当前状态选择适合的回应，而不是重复旧推荐。

讲义第 76 页。

它适合暴露“记住了过去，却没有更新现在”的问题。但从候选答案中选对回应，与在开放任务中正确使用偏好，仍不是同一个测试。

LongMemEval-V2：把环境经验变成同事式知识

该基准考察 Agent 能否从大量 Web 操作轨迹中积累环境经验，包括静态状态、动态变化、工作流、环境陷阱与前提意识。

讲义的图表展示了 451 个问题，题型包括选择题、简答与自由回答；因此不宜把它整体描述为选择题基准。历史可扩展到数百条轨迹，论文报告最长约 115M Tokens。

讲义第 83 页。

讲义同时比较了 RAG 式召回与文件系统加编码 Agent 的证据搜集。

讲义第 85 页。

文件系统方案在展示的设置中表现更好，但两侧使用的模型也不同；更强的模型与更主动的工具探索都可能贡献收益。这张图不能单独证明“文件系统天然优于向量检索”。 对生产选型，更有价值的是在相同任务、模型和预算下比较完整系统。

MemoryArena：跨会话经验必须帮助后续行动

MemoryArena 把记忆、Agent 与环境连接起来。任务包含相互依赖的子任务，前一轮的观察、反馈与偏好会成为后一轮的条件。

讲义第 88 页。

例如，群体旅行规划先获得成员需求，下一轮再追加预算或行程变更。系统需要用已有记忆修订结果，并通过可验证约束判断是否完成。

讲义中某些 Memory Controller 在这个设置下表现较弱，说明仍有很大提升空间。不过，任务完成率也依赖工具、规划和推理；不能把每一次失败都归因于记忆。

10. 三个仍未解决的问题

记什么，忘什么？

记忆写入时，我们并不知道哪些内容未来会重要。保存一切会增加召回、上下文和维护成本；删除过多，又可能丢失关键证据和未完成承诺。

一句话究竟是稳定偏好、临时情绪、引用他人的话，还是玩笑？仅靠“看起来像事实”不足以决定长期保存。

记忆可信度、隐私与用户控制

程序性记忆会影响未来行动，因此也是攻击入口。如果恶意内容被保存成“以后应该遵循的流程”，攻击影响就可能跨越当前会话。

讲义第 98 页。

记忆被召回，也不意味着获得了更高的指令权限。对用户来说，还需要看得见系统保存了什么、信息来自哪里，并能够纠正或删除。

检索到了，也可能用错

过度个性化就是典型例子：用户问一个普通问题，助手却因为读到了某项个人偏好，强行把答案往那个方向改。

更好的召回与训练可以缓解这种情况，但还需要判断当前任务是否真的需要个人信息。会使用记忆，也包括知道什么时候不使用。

它除了保存内容，还记录来源、适用时间、有效状态和替代关系。实际系统再根据权限、任务相关性与时间过滤候选，取回必要证据，然后提供给回答或行动模块。

    → 提取候选事实与经验
    → 对照已有记忆，判断新增、更新或不处理

    → 当前任务按需召回

评测也应覆盖整个链路：事实是否抽对、旧状态是否更新、召回是否准确、使用是否恰当，以及最终任务是否因此变好。

这也是我对这一讲的核心理解：一个持续工作的助手，既要保留经历，也要能够修正自己对经历的理解。可靠记忆来自存储、召回、更新与行动之间的配合。
