Anthropic Agent Skills

2026年10月24日 · 预计阅读 10 分钟

让一个模型“帮我写篇博客”并不难。难的是让它每次都记得保留源码、正确处理公式、补齐中英文版本，并在发布前检查页面。模型可能具备这些单项能力，却不了解这套具体的工作方法。

Anthropic 的 Agent Skills 解决的就是这类问题：把做事的方法、参考材料与脚本放进一个可复用的目录，让 Agent 在相关任务出现时再读取和使用。

CS 329Z：Agent Memory Architectures

2026年10月14日 · 预计阅读 14 分钟

一个助手可以在当前对话里给出很好的答案，但到了下一次会话，又需要你重新交代偏好、解释项目、重复上一轮已经完成的工作。它也许很会推理，却没有把这些能力接到一段持续的经历上。

Agent Memory 要解决的，就是这种跨时间的不连续：把过去的交互转成以后能够取回、更新，并正确用于行动的信息。

上一篇 Context Management Patterns讨论了每次模型调用应该看到什么。这篇进一步讨论：信息离开当前窗口之后，应该保存成什么、什么时候写入与召回，以及怎样证明记忆真的改善了后续任务。

                ↓
提炼：事实、偏好、经验、技能与任务状态
                ↓

                ↓
按需召回 → 进入工作上下文 → 影响下一次行动

CS 329Z：Context Management Patterns

2026年10月12日 · 预计阅读 11 分钟

一个编码 Agent 刚开始修 Bug 时，往往很清楚目标：找到原因、修改代码、运行测试。几十轮之后，上下文里却堆满了搜索结果、文件片段、终端日志和已经放弃的方案。用户最初提出的约束仍在历史里，但下一次决策未必还能正确利用它们。

长任务需要持续积累信息，也需要主动整理信息。Context Management 决定每次调用模型时，哪些内容进入上下文、哪些保存到外部，以及哪些细节暂时隐藏。

Stanford CS 329Z Lecture 6 把这件事归纳为五种模式：

1
2
3
4
5

Persistent Event Log   保存完整事件，按需重建输入
Memory Offloading     将知识移到记忆或文件
Compaction            用摘要替换较长的历史
Observation Masking   隐藏旧工具输出，保留行动线索
Context Isolation     为子任务建立独立上下文

本文围绕这五种模式展开，并用同一个修 Bug 场景说明它们怎样组合。内容以讲义的 Context Management 章节为主；文中的任务摘要模板、组合流程与评测建议是我的工程化整理。

CS 329Z：Frameworks & Orchestration

2026年10月09日 · 预计阅读 11 分钟

一个模型能调用工具，并不等于我们已经拥有一个可以上线的 Agent。

真正的 Agent 系统还需要回答一系列工程问题：状态保存在哪里？失败后从哪一步恢复？上下文怎样重建？工具权限如何控制？长任务由谁调度？每一步如何追踪？系统变慢、变贵或答错时，又该怎样定位原因？

这些问题横跨不同层次，常被笼统地塞进“Agent Framework”这个词里。更清晰的理解方式是把系统拆开：

2
3
4

模型与数据
    ↓
LLM Program / Workflow        决定调用逻辑
    ↓
Agent Harness                 提供工具、记忆、上下文与执行环境
    ↓
Durable Orchestration         让长任务能重试、恢复并跑到底
    ↓
Telemetry + Evals             让系统可观察、可比较、可改进

本文根据我的 Stanford CS 329Z: Engineering AI Agents 笔记中 Lecture 5 的内容整理。重点不是教你押注某个框架，而是建立一张架构地图：每一层解决什么问题，什么时候值得引入，以及为什么同一个模型放进不同 Harness，最终能力可能差很多。
